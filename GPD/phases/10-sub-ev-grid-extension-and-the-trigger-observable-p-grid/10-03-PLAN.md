<objective>
Build the deposited-energy axis that the rest of the milestone lives on: 744 bins reaching
0.1 eV, at the v1.0 spacing, with the v1.0 edge set preserved exactly so that no archived
v1.x artifact has to be reinterpolated to sit on it. Then decouple the response matrix's
deposit axis from the archived Phase-4 CSV and make the per-column Monte Carlo sub-seed
depend on the deposit energy rather than the column index.

Purpose: ROADMAP Phase 10 success criterion 1 is the axis, and success criterion 2 forbids
silent reinterpolation of legacy artifacts. Those two are only simultaneously satisfiable
if the extension preserves the v1.0 edges exactly, which the obvious construction does not.
Output: the versioned grid function, the caller version-pin table, the decoupled deposit
axis, the energy-keyed sub-seed, and the tests that make the exactness checkable.
</objective>

  <name>Task 2: Source the response deposit axis from the grid and key the sub-seed to energy</name>
  <files>src/qpd_potential/response_matrix.py, tests/test_energy_grid_extension.py, GPD/phases/10-sub-ev-grid-extension-and-the-trigger-observable-p-grid/10-03-GRID-CONSTRUCTION.md, GPD/phases/10-sub-ev-grid-extension-and-the-trigger-observable-p-grid/10-03-SUMMARY.md</files>
  <action>
`response_matrix.load_E_dep_grid_eV()` currently parses `data/combined_dRdEdep.csv` to get
the deposit axis. That makes the response matrix's axis a function of an archived Phase-4
product, which cannot be extended without re-running Phase-4's Monte Carlo. Add a
grid-sourced path: deposit centres are the geometric means of `shared_energy_grid(version)`
edges, converted keV to eV. Keep the CSV parser available and unchanged so the archived
provenance stays readable.

Measure and report the difference. Planning found the CSV centres deviate from the exact
geometric means by up to 4.918e-7 relative (CSV first centre 10.144970 eV, exact
10.144972680282423 eV), and the archived `artifacts/stage1/response_matrix_*.npz` were built
on the CSV values. Record this in the construction note and state plainly that the
regenerated matrices therefore cannot be bit-identical to the archived ones, so plan 10-04
must not promise bit-identity.

Then fix the seeding. `build_matrix` currently does `child_seeds = ss.spawn(n_edep)` and
uses `child_seeds[j]`, so a column's sub-seed is a function of its ordinal index. Prepending
160 columns shifts every index and re-seeds every column above 10.14 eV, which would turn
any comparison against v1.0 into pure Monte Carlo noise and hide a real regression of that
size. Replace the ordinal key with a stable function of the column's deposit energy — for
example a `zlib.crc32` over a canonical fixed-precision string or the raw float bytes of the
centre, combined into the existing `SeedSequence([seed, crc32(design), crc32(variant), ...])`.
